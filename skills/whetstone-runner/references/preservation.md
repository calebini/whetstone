# Protection selection and bridge operation

First establish the desired review policy, editable boundaries and who supplies
semantic preservation judgments. Both modes require real authority for substantive
changes and separate source adoption. They cannot be mixed in one job.

## Verified promotion

Read the executing release's `docs/VNEXT_VERIFIED_PROMOTION_RELEASE.md` and the
verified sections of `docs/OPERATOR_QUICKSTART.md`. The qualified 0.2.0 source
selection supports standard/stateful-system, local macOS/APFS and a fixed standard
Phase 2 rubric; it is not automatic support for MVP, other profile sets or another
installed runtime. Verify horizontal/vertical/focused selection and exact recovery
support before promising it.

Prepare bound seed, authority map, protected invariants, scope and review/client
configuration using the published schemas and builders. Keep package/config
outside a nonexistent destination. Validate with the supported admission dry run;
initialization is a separate local mutation. Never copy another run's authority.
The Editor proposes structured changes; candidate assembly, deterministic checks,
semantic verification and promotion govern accepted draft authority. A Verifier
cannot grant product authority. Use status's exact gate and references rather
than edit projections or force a rejected candidate through.

## Bridge

The bridge remains available for its supported workflows and existing roots.
It relies on mechanical evidence or exact operator attestations for semantic
effects, not an implicit semantic Verifier. An approved launch surface is not an
attestation of unseen output. The retained procedure below applies only to bridge
roots; verified mode uses its own package and decision commands.

### Bridge procedure

Use this procedure after selecting the bridge for the requested protection and supported workflow. A general preservation request alone does not select this mode. The executing repo's `docs/PRESERVATION_ACTIVATION.md`, `docs/OPERATOR_QUICKSTART.md`, contracts and CLI are authoritative. Check the checkout's actual support; do not edit its qualification constant, create runtime markers by hand, or silently use an unguarded fallback.

## Prepare the job

- Preserve the requested workflow: an assessment-only request stays reviewer-only. Enforcement does not authorize an Editor or source apply-back by itself.
- For a new editing job, prepare a fresh isolated root with canonical `spec.md`, `spec.history.md` and `rounds/` paths. Legacy runs cannot be converted retrospectively; existing guarded jobs use their supported continuation.
- Generate a line inventory from an immutable exact-byte base snapshot. Prepare the approved scope and a bounded surface using the repo's schema and inventory helpers. Record the allowed/frozen sections and units, change types, admitted findings and specific sensitive permissions. Present any boundary needing approval in concrete terms; honor existing authorization without asking again for the same decision.
- Serialize the approved artifacts and compute exact-byte Refs. The user should review the boundary and effects, not construct JSON or hashes. Validate bindings, configured scope and current base before client execution. Use real approval identities and statements; never copy fictional fixture approvals.
- Configure `preservation_bridge.mode: enforce`, `capability_version: preservation-bridge-v1`, and `allowed_change_surface` as its confined path/SHA-256 Ref. `predecessor_report` is optional/null. Use the nested YAML in the repo guide, not dotted literal keys. No `--preserve`, report-only bridge mode or vNext editing key activates this path.
- Establish the existing nested-client payload authorization and invoke normal `live-phase1` or `live-focused-phase1`. Inspect status for `preservation_bridge.mode: enforce`; omission is `legacy_unguarded` and must not be described as enforced preservation.

## Review and continue

A proposal needing effect evidence pauses as `PAUSED_DECISION`. Read `latest_proposal` and the assessment from status, then use `preservation-review` to display the exact original/final lines, transformations and findings. Present the actual proposed effect and grouped correspondence. Ask only for missing decisions; permission to generate a bounded proposal is not attestation that the resulting wording is equivalent.

Record an authorized adoption through `preservation-attest` with the exact selected lines, kind, disposition, finding references, effect and rationale. It computes IDs and hashes. Never infer approval of deletion or weakening from “clarify,” a resolved finding, or reviewer silence. Missing evidence is expected pending work, not a reason to retry the Editor or bypass preservation.

Prepare an immutable request with `preservation-request`; preview `preservation-accept --dry-run`, then accept the approved request. Dry-run eligibility does not itself approve an effect. Acceptance revalidates and completes or repairs one retained operation; it invokes no model. Replay uses the same request, while changed same-base authorization/evidence uses a new immutable request without overwriting earlier reports.

After acceptance, read status and preview `resume --continue --dry-run` for supported Phase 1 continuation. Fresh editing needs authorization for the current accepted base; never silently rebase a surface or change frozen retry settings. Review-only closeout can verify accepted bytes without fresh edit authorization. Focused stability is not full Phase 1 readiness. Phase 2 still requires normal readiness, and generic Phase 2 technical resume remains unsupported; consult the repo for bounded closeout or local repair.

Keep source apply-back as the separately authorized strop operation. Convergence and preservation evidence do not grant source-write permission. This workflow is the qualified current-runtime bridge, not vNext verified promotion or proof of arbitrary prose semantics.
