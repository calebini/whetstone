# Preparation decisions

The matching repository's `docs/OPERATOR_GUIDE.md`, `docs/SCOPE_NOTES_GUIDE.md`
and `docs/OPERATOR_EXAMPLES.md` own the full explanations. This reference is a
portable routing aid when the skill is installed separately.

## Intent and scope

Infer the document's purpose, authority, expected depth and settled/open decisions
from the conversation and project guidance. Summarize material assumptions;
clarify when ambiguity changes the boundary, authority, cost or success criterion.
Do not impose document names or ask the operator to classify every line.

Scope intake directs this review, not system design. Include outcome, consumer,
flows/surfaces, exclusions/deferrals, depth and good-enough criteria. Reference
existing definitions. Avoid inventing architecture, schemas or failure policy to
fill the form. Design questions within scope can remain questions for the review.

Use the expected level-two notes headings and inspect the compiled contract.
The compiler is deterministic, not a general prose interpreter; missing headings
can create defaults, and the combined deferred/out-of-scope heading currently
compiles to deferred surfaces. Scope guides model judgment and also participates
in validation, exact bindings and finding handling. Approval must reflect actual
authority, not a fabricated name or copied fixture. Do not modify admitted scope.

## Schedule, budget and models

Recommend vertical for broad interacting concerns, horizontal for a specific
sequence of dependencies, and focused for one isolated profile. Early projects
often fit vertical; age alone is not the selector. These recommendations do not
change defaults or supported gates. Focused completion cannot stand in for a full
Phase 1 result.

Start from supported preset allowances and adjust with a reason within authorized
limits. Do not routinely ask users for round counts. Separate profile passes,
Editor operations, cycles, persisted round numbers, closeout, retries and measured
model calls. Explain the selected mode's exhaustion behavior. Disabled Phase 2
is not available spending authority. Timeouts and review counts are not a hard
monetary cap; do not invent unknown usage.

Resolve client, model, reasoning effort and timeouts per active role. Reuse local
preferences when supported and expose effective settings. The legacy Codex helper
in the inspected checkout fixes medium reasoning; do not invent a YAML setting
or claim a preference is honored without checking the adapter. Verified identity
settings use their bound contracts. Record limitations instead of changing code
or the selected runtime as part of ordinary staging.

## Package and handoff

Use explicit input selections and retain document ownership. Linked documents
are not automatically included. Snapshots, inventories and exact hashes are agent
bookkeeping. Use only supported package/build/validation paths; no new preparation
CLI is implied. Bridge and verified fresh-root procedures differ.

Separate technical readiness from authorization. Report purpose, inputs and
boundaries, execution settings/limits, checks completed, unresolved choices and
next action. Preparation does not require model calls. Reuse in-scope data-sharing
and launch authority; ask only for a genuinely missing decision. Host execution
permission and provider authorization are distinct. Source adoption is separate.
