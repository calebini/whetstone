# Whetstone release checklist

Use the steps that apply to the requested milestone. A readiness review can end with a tested candidate. Treat a production suite activation, stable promotion, push, tag and publication as distinct actions. Carry forward authorization already given for each.

Read the target checkout’s `docs/specs/RUNTIME_DISTRIBUTION_AND_SELECTION_SPEC.md`, the active entry in `IMPLEMENTATION_PLAN.md` and its linked qualification record. Resolve the launcher and agent skill directory from the calling environment. Use `whetstone --runtime-info` to find the executing installation.

- [ ] **Establish the baseline.** Record the source commit, worktree status, candidate identity, stable version and resolved stable target. Identify the exact change, supported selections and exclusions. Check which existing receipts still match the relevant source and contracts.
- [ ] **Qualify the candidate.** Build a separately versioned installation. Exercise the changed path through its public CLI with synthetic inputs. For a suite activation, verify the authorized digest against the installed manifest and production map. Check admission, a meaningful refusal, retained-job re-entry and adjacent supported modes. Distinguish scripted clients from live-provider evidence. Use live calls only within the approved payload and budget.
- [ ] **Finalize and install.** Align the package and runtime version, release notes, operator guidance and repository-owned skills. Install from the exact release commit into a new versioned directory with its own environment. Verify the launcher reports that version, commit and target. Check installed contract resources and repeat CLI admission against the final installation.
- [ ] **Promote and verify.** Save the previous stable target for rollback. After the agreed checks pass and promotion is authorized, swap the stable symlink atomically with a temporary symlink and `os.replace` in the same directory. Verify default and explicit stable selection, command help and a representative admission dry-run. If the post-switch check fails, restore the saved target atomically and verify the old launcher.
- [ ] **Reconcile calling-agent skills.** Before promotion, compare the candidate’s complete Whetstone skill folders with the copies the agent host actually discovers. After promotion, use the target reported by the default launcher as the source for syncing release-owned files, including references and agent metadata. Inspect differences for local customizations before copying. Account for added and retired files and compare the resulting trees. Keep personal defaults separate. On rollback, repeat this check against the restored version. For a release-preparation skill introduced after an older release was built, use its identified maintainer checkout until the skill ships in a release.
- [ ] **Test from a consuming project.** From an unrelated directory, run `whetstone --runtime-info` using ordinary PATH lookup. Follow the installed runner skill to the executing runtime’s guide. Check that its advice matches a newly supported workflow and a relevant limitation. With a prepared synthetic consumer-3 package, for example, run `whetstone vnext-admit --root <fresh-root> --config <config> --dry-run` and confirm the root stays absent. A prebuilt package checks invocation and admission. To assess staging ergonomics, also try starting from a sample spec and the published instructions.
- [ ] **Record the rollout.** In the existing release record or local deployment receipt, capture the exact commit and suite, checks and results, stable and rollback targets, skill differences reconciled, and any remaining operator decision. Update current handoff notes that still describe stable adoption as pending. Keep earlier qualification results labeled with their original version.
- [ ] **Tag the deployed commit when authorized.** Read the version and full commit from the verified stable launcher. Check the local and remote release tag before creating it. If an existing tag resolves to a different commit, report the conflict and leave the tag in place. Create an annotated tag at the explicit deployed commit and push that specific tag when authorized. Verify its remote commit target against stable even if later closeout commits have advanced the branch.
