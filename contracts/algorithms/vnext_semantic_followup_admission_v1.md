# Semantic follow-up admission v1 (unactivated)

This consumer admits an explicitly selected, already committed interpretation answer into a fresh same-round transaction. It requires the exact follow-up preflight/answer contracts plus its own algorithm and two closed schemas. It changes neither the source candidate's final decision nor current verified authority. It does not fabricate another Reviewer pass, infer an answer or expand the original editing scope.

Each follow-up retains `rounds/round-N/transactions/<transaction_id>/admission.json`, `mutation_plan.json` and `proposal_handoff.json`. Its proposal and candidate remain in their existing content-addressed round directories. The original round-level input, v2 plan and handoff remain unchanged. The admission record binds the real Reviewer round, base pointer, exact source creation and final verification, answer receipt, independently admitted editing-plan hash and new mutation-plan hash. The consumer reproduces all of these from original evidence on every load; a cached follow-up snapshot is not admission authority.

A final rejected source candidate can commit one selected follow-up transaction through `<source-candidate>/followup_transaction.json`. Multiple interpretation answers may exist, but this marker explicitly names the admitted transaction input; there is no latest-answer rule. Under the storage writer lock, validate the complete current registry, require no registration orphan and require the source still latest for a new selection. Reproduce the answer and v3 plan, repeat source semantic/decision and answer durability barriers, publish the transaction input, then publish the selection marker last. An input without the marker is prepared and cannot invoke a client. Exact selection reentry validates and returns its existing reference; a different answer cannot overwrite the selection. Submission and registration recovery retain exact identities and timestamps.

Historical source validation uses a read-only creation-prefix view ending at the source's actual committed creation ordinal. Every creation/preparation/material in that prefix is replayed. The numeric journal must remain contiguous. This is evidence about an ancestor, not proof of current global health or permission to write: the wrapper exposes only reads, and registry registration/reconciliation refuse. The outer admission/operation validates the complete applicable registry and current base. A follow-up source must strictly precede the consuming historical boundary, preventing self-reference and cycles. Later candidates and their input loaders cannot recursively become evidence for their own ancestor.

Proposal input routing selects the exact proposal's transaction from its canonical patch and immutable admission record. Initial transactions replay the original round admission. Follow-ups replay their source proof through the historical prefix and regenerate their full preflight, including the selected interpretation. Registration receives the exact transaction plan reference from the validated handoff, rather than a round's latest plan. Registered semantic context uses that same exact proposal input resolver. All existing v2 round paths retain their previous behavior.

Before request or registration work, the selected transaction guard validates the full registry. The latest committed candidate must be its source or the candidate produced by that transaction; unrelated later candidates make it historical. A sole registration orphan may proceed only when its preparation names this selected transaction and round; the registry must then reproduce and reconcile it before accepting anything. Historical reads and exact admission reentry are not permission to invoke work against a superseded selection. Existing bounded request journals still own attempt allowances, interruption and completed reentry; a final candidate cannot reopen.

Normal semantic decisions/requests must independently validate the newly registered candidate under its own transaction identity. Complete command routing, status/continuation integration, release qualification and an answer-driven retained native journey remain obligations of the full 18.6 bridge. This component alone does not activate a shipping suite or complete that slice.
