# Semantic follow-up workflow v1 (unactivated)

This consumer connects the exact follow-up admission protocol to the existing semantic proposal status, closeout and explicit-continuation workflows. It requires its own pinned algorithm plus all normal semantic workflow and follow-up admission contracts. Command activation must separately qualify this consumer; installed files or a partial older semantic suite do not enable it.

For an explicitly selected Reviewer round, resolve its last candidate through committed creation order, not directory names or timestamps. If that candidate has a committed follow-up selection marker, the marker's exact transaction input is active. Otherwise, a candidate produced by a follow-up resolves its own canonical transaction input and source selection. An original v2 candidate retains the original round admission. An answer receipt alone, an uncommitted transaction input or an unrelated round cannot select work. Read-only resolution validates the actual source creation, selection and reconstructed transaction.

Each command view pins the resolved reference for its selected round. Its writer authority callback rereads the current committed selection and refuses a changed selection before work. Candidate registration of that same transaction does not change the reference. Historical proposal routing remains separate from active selection and always reconstructs each exact transaction. A deliberate admission operation can discard that command object's old view only after explicitly committing its own selected follow-up; an ordinary status/reentry cannot do so.

The view reuses existing proposal status, initial decision closeout, semantic status and semantic continuation code. It does not introduce a separate retry policy or bypass D7's processing gates. Initial-decision, Verifier-result, final-decision and terminal-report recovery therefore retain the normal explicit-continuation behavior and finality rules. The original round record, Reviewer classification and input bindings remain immutable when a follow-up executes.

Read-only status may show an already explicitly admitted follow-up as not yet proposed, but cannot admit one or choose among answers. Ordinary live execution can work on that committed selected transaction; completed reentry remains read-only at the command layer and constructs no unnecessary adapters. A source decision and its historical outstanding IDs remain unchanged after the child is verified or rejected. Current verified authority stays at the seed in P mode.

Public CLI answer/selection surfaces, complete recovery and repeated-follow-up qualification, retained native command journeys, D8 and release qualification remain required before shipping. This workflow component does not by itself change any qualification map or enable a mode.
