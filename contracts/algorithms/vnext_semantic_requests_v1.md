# Durable semantic requests v1 (unactivated)

One logical Verifier request binds an exact registered candidate, immutable semantic context, configured role, dedicated prompt and provider schema. Its ID is `req_` plus SHA-256 of canonical JSON `["whetstone-logical-client-request-v1", job_id, "verifier", "phase1", "semantic_verification", transaction_id, candidate_id]`. State lives at `rounds/client_requests/<request_id>/`; caller directories cannot reset the allowance. The immutable descriptor must select semantic-policy-v2, and this request's five schemas and algorithm must be pinned in addition to the registered context consumer's dependencies.

An invocation requires a committed, non-final, deterministic-pass candidate decision. The current owner reader supports the first proposal-only decision; later ordinals need the separate decision-journal extension. Every new invocation rechecks that gate under the local storage lock. The request never invokes an Editor or changes candidate/draft authority.

The canonical request header binds job/transaction/candidate, role/phase/gate, exact context hash, creation reference, base pointer, original prompt hash, transport and hard limits of two invocation slots and one automatic shape retry. Context bytes and original prompt are retained before the first invocation marker. The initial marker exactly matches the claimed transport, including timeout. An explicit later continuation may change timeout only; role/model/version, command, working directory and provider schema remain fixed. Each marker binds the exact prompt and previous outcome hash. A durable marker consumes its slot even if process start or response capture is uncertain.

Only a newly decoded `SemanticShapeError` permits the one automatic retry. Missing/invalid binding, coverage or policy evidence is `invalid_semantic`, which cannot be retried under this request. Timeout, transport failure and interrupted invocations require explicit continuation. Two markers exhaust the allowance. Valid semantic pass/reject/operator verdicts all close the request successfully and cannot cause semantic repair or Editor reruns.

Every attempt retains its exact prompt, marker, raw response when present, optional descriptive telemetry, and an outcome. An outcome with raw evidence must reproduce by decoding those exact bytes. Without raw bytes, only a concrete timeout/transport/interrupted outcome is valid; a bare marker derives interrupted state. Missing raw referenced by a valid result, missing bound predecessor, gaps, unknown slots/files, changed context/prompts and altered transport refuse. Prepared prompt/context files can be completed by exact replay before a marker; they cannot stand in for an invocation.

Read-only inspection reconstructs technical/result status and does no repair. Before a new invocation or successful materialization, writers repeat exact retained evidence barriers, including creation-event acknowledgement and prior invocation/raw/outcome records. Publication uncertainty propagates through the storage kernel; it is never silently retried with a stale token. Existing deterministic registration dependencies precede the creation event's publication and were durable before it could be exposed.

For a valid response, materialize the exact optional authority request at the decoder's canonical candidate-relative locator, then `<candidate directory>/semantic_verification.json`, and commit the closed result receipt last. The receipt binds request/context/creation, exact raw response and derived report/request references plus verdict. No report or request is trusted without matching raw evidence, even before a receipt exists. Unexpected or contradictory prepared outputs refuse before any writer proceeds.

`finish_semantic_request` accepts no client. It redecodes retained valid raw output, repeats source barriers and completes missing derived artifacts/receipt without consuming another slot. `run_semantic_request` likewise takes the completed/materialization path before accessing a client. Invalid/exhausted reentry can persist reconstructed outcomes but cannot call a client. All readback validates exact report/request contents and receipt relationships; receipt existence alone is insufficient.

Completion means evidence is ready for a separate append-only candidate decision consumer. The request neither verifies/rejects the candidate nor advances the current verified pointer, seed history, review debt, Phase 2 eligibility or source apply-back. A semantic operator request grants no authority changes or effects and requires a new transaction after response. Public workflow availability and D8 audit/reconciliation remain release gates.
