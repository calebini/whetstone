# Semantic follow-up preflight v1 (unactivated)

An explicitly selected semantic interpretation may inform a fresh transaction within the editing scope already admitted for its finally rejected source candidate. The interpretation grants no new effects. This component constructs the new plan and request context; durable transaction admission, transaction-specific handoff/registry replay and command routing remain required consumers before this workflow can ship.

The consumer pins this algorithm, `mutation_plan_v3`, the semantic answer schemas and answer algorithm, in addition to the source proposal/semantic contracts. A supported descriptor alone or installed files do not imply this additional qualification. Old preflight calls without semantic follow-up evidence retain their exact input identity, plan version and prompt.

The storage reader selects an exact candidate and answer receipt, validates the complete source registration/semantic decision chain and original question, and requires the source candidate still current when preparing new work. A decline cannot supply follow-up input. It returns canonical, closed evidence containing source context, source final verification and reference, question, response, receipt and exact receipt reference. This evidence is a snapshot for pure preflight; it is not an admission receipt or permission to invoke an Editor. The eventual durable admission consumer must freshly reproduce it from its original immutable sources on every load and under writer exclusion before publication or invocation. Cached snapshots alone cannot authorize work.

Pure preflight reconstructs the original v2 editing plan from the retained Reviewer inputs and applicable unit decisions. It checks that the source plan is either exactly that v2 plan, or a v3 plan whose projection reproduces that same v2 editing plan. The source job, seed, base, map, authority, scope, invariant program, role configuration and base pointer must remain identical. The question/answer binding is reproduced under its pinned policy; the receipt must bind the exact source final rejection and selected non-decline response. No classification, finding, slice, constraint, target, existing derived task or named-unit grant is added or expanded.

`mutation_plan_v3` retains every v2 editing field and adds `semantic_origin`: the source candidate and transaction IDs, reconstructed v2 editing-plan hash, exact answer receipt reference and source final verification reference. Its existing transaction identity algorithm includes this entire versioned plan body and the original effect-bearing response hashes. Thus exact reentry yields the same new transaction; another answer or source candidate yields a different transaction. The interpretation response is not added to effect-bearing responses or deletion authorization. A follow-up's transaction must differ from its source transaction.

The Editor prompt keeps the original admitted finding details and limits, substitutes the exact v3 plan and its hash, and includes the bound question, explicit response and receipt as interpretation evidence. It states that the source candidate remains rejected and that the interpretation changes no authority precedence or editing scope. The independent Verifier must receive the same interpretation evidence when the eventual registered-context consumer is connected. Both deterministic and semantic verification remain mandatory for the new candidate; no old verdict is transferred.

Repeated follow-up can retain the same independently admitted editing scope while binding a new final rejected source candidate and answer. A correction requiring effects outside that scope must obtain separate applicable authorization or use a new job when descriptor-bound policy changes. This component neither changes authority precedence nor manufactures a Reviewer pass to allocate another transaction.
