# vnext-contract-invariants-v1

The offline foundation checks closed shapes and immutable artifact relationships. Passing it does not establish patch assembly correctness, semantic truth, current filesystem authority, successful promotion, scheduler readiness or source-write permission. Later slices must supply those implementations and their gates.

Validation order: load the manifest with the implementation's known manifest schema; recompute its canonical digest excluding only suite_digest; match the implementation registry's exact version/digest pair; read every pinned relative file without symlinks; compare byte hashes; reject unsupported schema keywords/formats or unpinned transitive references; run every declared fixed conformance vector; then validate descriptor and artifact bindings. A supplied digest is not a supported-suite selection. Revalidation detects files changed after an earlier successful check. A manifest may not hash itself or its registry. Conformance inputs use independent literal digests, so their bytes do not depend on their containing suite digest.

Schema validation supports only the documented subset enforced by VNextSchemaRegistry. Unsupported keywords are errors, never silently ignored constraints. This suite uses type, properties, required, additionalProperties (boolean or schema), package-file or same-file JSON-pointer $ref, $defs, const, enum, allOf, anyOf, if/then, items, minItems/maxItems/uniqueItems, minLength, pattern, format=date-time and integer minimum. title/description/$schema/$id and x-whetstone are annotations; same-file references are qualified against their actual containing file, and references otherwise use package filenames rather than URI-base resolution. Object properties/definitions are recursively audited. JSON booleans are distinct from numeric constants and enum values.

The public minimum shapes come from the candidate leaf. An offline `candidate-index-v1` contains job_id and an ordered array of {candidate_creation_ordinal,path,hash} creation-event references. It is an interchange view of the immutable contiguous creation chain, not a new runtime authority pointer. Ordinals begin at one, bind the exact preceding event hash, and cannot duplicate a candidate. The initial disposition event and candidate section map must be hash-bound by registration. Prepared unbound artifacts are not effective events.

`review-configuration-v1` is a pre-job input with workflow, review mode, profile set, named profile budgets and reviewer/editor/verifier identity objects. It contains no commands, host paths, job IDs or runtime authority. The descriptor pins its canonical hash; an offline bootstrap caller supplies its path alongside the descriptor because the descriptor has no review-configuration locator field. The optional existing scope-contract shape is reused only as an approved immutable pre-job input, serialized with vNext canonical bytes.

Authority: exactly one mutable target matches the seed; other roles cannot mutate. Excluded content is not read. Only allowed roles may introduce requirements. Authority scopes are exact symbols, multiple roles for one file must have disjoint scopes, and every multiply-normative scope needs an exact precedence order. Binding and assertion IDs are recomputed. Invariant matcher/enforcement kinds must agree; a semantic assertion is never proved by a lexical test.

Mutation: all base/job/input hashes agree. Admitted findings must be editor-fixable; slices form an acyclic graph and cover exactly the admitted set. Response identities and exact hashes match the transaction; deletion units have explicit operator authorization. Patch dependencies are acyclic, target/preimage/plan/payload bindings agree, types and numeric caps remain within the plan, and every operation cites admitted work. Sensitive effect claims require derived tasks citing operator responses. Actual payload grammar, overlap-after-operation preimages, assembly and unit-level effect proof remain 18.4/18.5 gates; these offline checks cannot substitute for them.

Reports: job/transaction/candidate/base/map/patch/algorithm hashes agree. Passing preservation claims cannot contain known failures, over-budget changes or unauthorized units. Semantic finding coverage equals the admitted set; assertion coverage equals the semantic invariant set. Uncertainty needs exactly one mapping per uncertain field. Loss/unrelated-change uncertainty rejects; a decision mapping names a decision. Passing semantic claims require resolved findings, no unrelated/lost semantics, authority compliance and passing blocking assertions. Validation checks the claims' consistency, not whether natural-language evidence is truthful.

Verification/disposition: a verified decision needs matching passing reports, no outstanding decisions/rejection codes and a final decision. Rejections are final with reasons; unverified decisions are non-final. Promotion permission also requires verified_promotion mode. Decision/event ordinals and predecessor hashes are contiguous; verification pointers bind both the exact decision and its event in the registered candidate directory. Event forms and transitions follow the candidate leaf. Prepared events alone cannot determine terminal disposition.

Promotion/current pointer: seed pointers have ordinal zero and null candidate lineage. Subsequent pointers bind the exact registered candidate/map, final verified decision, intent, promotion event and preceding ordinal snapshot. Intent base/current-pointer expectations and next ordinal agree. The current pointer and same-ordinal history snapshot must be byte-identical. These predicates validate evidence relationships; they do not acquire the D8 lock, choose a runtime claimant or execute pointer replacement.

Terminal readback selects the highest valid creation ordinal and then its commit-bound promotion, verification or initial event, in that order. Every copied identity/hash/disposition must match. Unpromoted work and outstanding decisions cannot claim apply-back. Scheduler/convergence, source-hash and lock/runtime gates remain independently required.

Descriptor algorithm bindings recognized by this contract suite are markdown-atx-v1, patch-assembler-v1, preservation-inventory-v1, whetstone-canonical-json-v1 and semantic-policy-v1. Recognition defines frozen contract names, not availability of the later parser/assembler/verifier services. New algorithms or changed suite bytes require a new published suite version and registry binding. vNext runtime modes remain unavailable through this offline release.

Fixed conformance operations: schema (schema name plus JSON value), canonical (JSON value to exact UTF-8 hex), candidate_identity (the five ordered candidate inputs), topology (items/key/dependencies to stable order), and decision (decision/preservation/semantic/job context). Vectors have name, operation, input, expected_result=pass|reject, expected. Unknown operations and envelope fields are invalid. Expected rejects must actually reject; successful outputs must equal the fixed expected value. Fixture data is never imported or executed as code.
