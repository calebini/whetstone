# Semantic verifier context v1 (unactivated 18.6 component)

This pure builder prepares immutable, complete input for independent semantic verification. It neither invokes a model nor writes any file. Registration admission, a supported consuming suite, read-only native invocation, output validation, uncertainty policy and append-only candidate decisions remain separate gates. This supplement is proposed and unregistered.

The storage caller must supply exact committed candidate creation evidence and the admitted transaction's input arguments, proposal, candidate bytes/map, preservation report and inventory. `prepare_semantic_context` replays unit preflight to reconstruct the actual mutation plan, admitted findings, derived tasks, named operator grants, dependency context, base inventory and discovery rules. It validates creation/proposal identities and exact job, round, transaction and proposal associations, canonical candidate and creation locators, and creation-bound candidate/map hashes. It then independently reproduces the deterministic assessment and semantic obligations. Deterministic failure or altered inputs refuse before a context is returned.

An event's plausible shape and identity do not prove it committed. The storage caller must validate the creation journal, immutable handoff, admitted suite and committed base history before using this builder. The existing registered-candidate test exercises actual readback; that test does not qualify a shipping verifier workflow.

The internal context has `context_version = vnext-semantic-context-v1`. It is canonical JSON held as immutable bytes, not yet a persisted public artifact or a verifier response contract. Its input hash is SHA-256 of those exact bytes. Reading `SemanticContext.packet` returns a new detached object; mutation of that object cannot change retained input bytes or hash. A future durable request must pin this context algorithm and bind these exact bytes, all response schemas and the separate verifier prompt before claiming an invocation.

The context includes:

- the immutable descriptor, suite version/digest, complete role configuration, exact base pointer and committed creation event/reference;
- complete seed, base and assembled candidate text, their maps, and both complete unit inventories;
- the reproduced mutation plan, every admitted finding's original finding and exact Reviewer evidence, and any narrower derived task;
- authority map, approved scope, protected invariants, and exact admitted dependency bytes alongside each complete authority binding, including role and effective horizon;
- exact request/response pairs for named unit authorization;
- the exact patch and complete payload bytes under an explicit label identifying Editor claims as untrusted evidence;
- the independently reproduced preservation report and complete hash-bound semantic obligations.

Dependency bytes must be exactly the admitted context set and match their bound hashes. Excluded or undeclared contents cannot be added as extra Verifier context. The full authority map remains present so excluded roles and precedence are visible without exposing excluded document contents. The mutable target is represented by the complete immutable seed/base/candidate evidence.

The Verifier's configured model may equal the Editor's model under the minimum independence policy. This builder preserves the separately pinned Verifier role; it does not establish invocation independence. A separate verifier-specific prompt, native read-only capability boundary and separately validated response are still mandatory. Editor resolved/unresolved statements and normative-change claims never become authority through inclusion in the context. Structural correspondence is likewise an assessment obligation, not proof of equivalence.
