# Local Storage Contract (D8)

Status: **design ratified by the operator on 2026-09-15; bounded consistency audit and consuming-release qualification pending**. The operator explicitly accepted the single-host storage recommendation and requested ratification. This resolves the storage policy choice; it does not claim an audit pass, complete slices 18.5–18.7, register a suite or activate a runtime mode.

The [candidate leaf](CANDIDATE_EDITING_AND_PROMOTION_SPEC.md#local-storage-decision-d8) owns registration, candidate finality and promotion semantics. This normative supplement selects their single-host exclusion, fencing and durable publication protocol, named `vnext-local-storage-v1`. The artifact and scheduler leaves retain ownership of their artifact and lifecycle contracts.

## Ratified operating model

One host operates one canonical local run root. There is one owner of authority mutation at a time; overlapping mutation attempts while ownership is held receive a retryable busy result. This protects against accidental overlapping commands or workers. It does not introduce concurrent authoritative writers as a product feature. Read-only status does not mutate or repair the run. A sole writer must still recover safely after interruption.

Remote model execution does not make the model another authority writer: model output is retained and admitted by Whetstone. Parallel proposal generation, distributed writers and writable synchronized replicas are outside this decision. No new parallel execution is authorized or implemented by ratification.

## Binding and supported environment

The consuming release MUST publish a new descriptor-bound contract suite that pins this document, its storage-envelope schemas and conformance vectors. The frozen `vnext-contracts-1` suite remains unchanged and does not gain registration or promotion support by file presence. A descriptor selecting that earlier suite remains governed by its earlier qualified capabilities; no in-place descriptor upgrade is allowed. Storage protocol selection follows the registered suite, not a user-supplied path or unrecognized configuration key.

P0 supports one host, one canonical physical run root and cooperating Whetstone writers on a qualified local filesystem. The first implementation target is macOS/APFS; another platform/filesystem needs its own recorded process, durability-primitive and fault-injection qualification before it is advertised. Network filesystems, shared roots across hosts, cloud synchronization, filesystem rollback beneath active processes, moving/replacing an active root, and concurrent direct artifact edits are unsupported. An offline byte-identical root copy can be inspected; it is not a second writer to the original run. Active clients receive no write access to transaction authority.

Every authority directory and file MUST remain on the admitted root's device, with no symlink traversal. Unsupported filesystem detection, failed required primitives or a detected root/device/inode change MUST fail closed before further publication. Claims cover cooperating-process concurrency, process termination and correctly honored durability primitives. Tests MUST distinguish injected process/persistence failures from physical power-loss testing; the latter MUST NOT be claimed without such evidence.

## Fresh-root initialization and physical identity

Initialization MUST exclusively create a fresh root and refuse any existing root, including an empty or partially initialized root. It MUST NOT repair interrupted initialization, upgrade a reviewer-only/legacy root, relocate a root or silently rebind a copied root. Preserve interrupted evidence for inspection. The caller MUST validate and supply the complete descriptor, seed and initial authority set before initialization; the kernel's canonical descriptor/job/hash checks do not substitute for domain admission.

Initialization durably publishes the initial byte artifacts and permanent lock, then publishes `rounds/authority_storage.json` last. That immutable canonical `vnext-local-storage-binding-v1` record binds job ID, canonical absolute root path, root device/inode, APFS filesystem identity, retained lock device/inode and byte hash, and immutable descriptor path/hash. Its exact fields are defined by the [storage-binding schema](../../contracts/schemas/vnext_local_storage_binding_v1.schema.json), which remains outside any shipping consuming suite until qualification.

This physical binding MUST remain separate from content-derived job identity: machine paths/inodes MUST NOT enter the D6 job preimage. Another process MUST NOT admit a byte-identical replacement lock or copied root as the original writable authority. Validate the physical binding, immutable descriptor and retained lock identities on acquisition and each publication. There is no writable relocation/rebinding procedure in this contract.

## Persistent lock identity and ownership

Seed initialization for the consuming suite MUST create and durably publish `rounds/.vnext-authority.lock` before admitting further writers. It is a regular file with exactly one link. Its inode MUST NEVER be unlinked, renamed, replaced or repurposed by Whetstone. Existing admitted roots with a missing, non-regular, multiply-linked or symlink lock MUST halt artifact-invalid rather than recreate it. The old reviewer-only lock is not the D8 lock and is not an upgrade mechanism.

All post-initialization authority mutation uses one storage object keyed by physical run root plus immutable job ID. Registration, verification-pointer publication, promotion preparation/commit and pointer-derived materialization MUST acquire an exclusive nonblocking kernel `flock` on that retained inode. Lock contention is a retryable busy result with no client call or transaction mutation; it is not evidence corruption and does not change candidate disposition. Read-only status acquires no exclusive lock and never repairs.

An acquired token is opaque, nonserializable and process-local. It binds the job ID, root device/inode, lock device/inode, live descriptor, acquiring PID and a new unpredictable acquisition nonce. A process-local mutex serializes token validation, each mutation syscall and token invalidation/close, so an asynchronous release cannot occur between a successful check and a write. No public API accepts a copied token dictionary or a bare path in place of this capability. The storage adapter alone owns the lock descriptor and MUST NOT expose unlock, duplicate or transfer operations to callers.

The token becomes valid only after kernel acquisition, locked validation of the immutable descriptor/seed lineage and matching root/lock identities. Each artifact publication and pointer replacement MUST recheck the live token, PID, descriptor and path identities under the same mutex. All supported writer entrypoints MUST use this adapter; bypassing it is a programming defect. Authority is the continuously held kernel lock, not the nonce, PID, timestamp, a lease file or a client claim. No finite lease, heartbeat timeout, PID probe, force-unlock or lock-file deletion can transfer ownership.

On orderly release, invalidate the token before closing the descriptor. Never reuse a token, including after reacquiring the same inode in the same process. A process-wide gate MUST serialize descriptor transitions, publication and fork callbacks. Stores MUST be closed explicitly or through a context manager. Descriptors MUST be close-on-exec. Forked children MUST invalidate inherited tokens and close inherited descriptors without issuing `LOCK_UN` (which could release the parent's lock), discard inherited store registrations and reset inherited process-local mutexes. No client subprocess may inherit the lock. A former holder, a fork child and a copied/replayed token MUST be rejected before a write. Process death releases ownership when the final descriptor reference closes. A suspended live holder retains exclusion; reclamation means ordinary acquisition after kernel release, followed by reconciliation. This is local storage-backed fencing for cooperating writers; it does not claim that an advisory lock prevents an arbitrary process from writing files directly.

## Durable publication

All mutations below are performed with a valid token, except exclusive first-time seed initialization. Inputs and completed artifacts are immutable; temporary files are never authority.

1. Create missing directories through the adapter, synchronizing each parent after creation. Create a uniquely named temporary file in the destination directory using exclusive creation; write exact canonical JSON or exact raw bytes, flush and synchronize the file.
2. For immutable publication, link that temporary inode to the final name using create-if-absent semantics. If the name exists, validate regular-file confinement and accept only byte-identical replay; otherwise halt artifact-invalid. Never overwrite an immutable artifact. Synchronize the destination directory, remove only the adapter's own temporary name, synchronize that directory again, and fully flush the published regular inode before acknowledging durable publication. Byte-identical replay of an existing artifact MUST repeat the durability barrier.
3. For the mutable current-pointer commit, first durably publish the exact ordinal history snapshot and all its dependencies. Under continuous ownership, reread and validate the expected current pointer's exact bytes/hash and ordinal. Rename a synchronized same-directory temporary containing byte-identical snapshot bytes over the current pointer, then synchronize the containing directory. There is no unlink-then-write interval. This locked compare-plus-rename is the conditional commit; rename alone is not a compare-and-swap primitive.
4. Candidate-local verification pointers follow the same locked compare-and-replace rule against their expected prior state and durably published decision/event dependencies. Pointer-derived mirrors may be replaced only from validated committed lineage and under the same exclusion.

On macOS, synchronized file publication requires `fsync` followed by `F_FULLFSYNC`; containing-directory synchronization and a subsequent full flush on the published regular file complete the required ordering barrier. Unsupported/full-flush failures MUST be surfaced, never silently downgraded. Other qualified implementations MUST publish their equivalent primitive sequence. A filesystem/device that does not honor these primitives is outside the guarantee.

Publication results distinguish `not_committed`, `committed` and `outcome_requires_reconciliation`. This classification applies to immutable link publication as well as pointer rename, including cancellation raised inside publication. An attempted publication with a failed acknowledgement or post-publication barrier is uncertain; uncertainty MUST invalidate and release ownership. Domain transition validators MUST enforce ordinal, ancestry, dependencies and eligibility; the storage primitive does not infer these from file names or existence. An exception before the authority-replacing syscall leaves the old pointer authoritative, though immutable prepared artifacts may exist. Once replacement has been attempted, a failed syscall acknowledgement or durability barrier MUST NOT be reported as a known uncommitted transaction or followed by rollback, another ordinal or another client invocation. Preserve evidence, release ownership and return a halted/recovery-required result. A new acquisition validates the actual current pointer and its immutable same-ordinal history/dependencies before classifying the outcome. Only a valid old or valid new committed lineage is usable; torn, missing or contradictory authority halts artifact-invalid. A read-only observer may see the new pointer after rename and before durable acknowledgement, but MUST NOT repair or grant source-write permission from an in-progress observation.

## Reconciliation and ordering

The existing candidate-leaf ordering remains normative: validate current committed lineage before searching for a next-ordinal claimant; recover committed materializations without reopening pre-commit work; otherwise reconcile the sole valid prepared claimant before selecting the highest registered creation ordinal. Registration and promotion use this same retained lock. Registration MUST reconcile the one next creation-ordinal orphan before allocating a later ordinal. A prepared promotion claimant keeps its reservation if a newer candidate subsequently registers. Epoch, nonce, timestamps and directory order MUST NOT choose a candidate or ordinal.

Every recovery invocation reacquires ownership and reconstructs authority from immutable evidence. It does not inherit the failed invocation's token or trust a saved lock-owner record. Incomplete temporary files have no authority; cleanup may remove only recognized uncommitted adapter temporaries under ownership, and is unnecessary for status. Missing or conflicting immutable committed dependencies cannot be manufactured or repaired from mirrors. No lock error may label an unverified candidate verified, make a prepared event effective, or advance a pointer-derived consumer.

## Required qualification

The consuming slices MUST demonstrate: two competing processes share one exclusion domain; no registration/promotion overlap; paused holder blocks takeover; owner death permits reacquisition; stale/released/copied/forked tokens cannot mutate; child cleanup cannot unlock the parent; executable clients inherit no lock; missing/replaced/symlink/multiply-linked lock refuses; root/device identity changes refuse; immutable replay accepts only identical bytes; directory and file flush failures are surfaced; current-pointer readers observe complete old or complete new bytes; expected-pointer mismatch refuses; interruption at every registration/verification/promotion prefix is reconciled in candidate-leaf order; rename acknowledgement and post-rename flush failure trigger readback rather than rollback; read-only status changes no byte; legacy and bridge paths retain their existing behavior.

## Primitive references (informative)

Apple documents that flock is advisory and fork/dup share the lock, including the risk of a child explicitly unlocking its parent's lock: [flock(2)](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html). Apple distinguishes host flushing from the stronger device flush needed for ordered persistence: [fsync(2)](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html). The Linux reference describes atomic destination replacement and the separate need to synchronize directory entries: [rename(2)](https://www.man7.org/linux/man-pages/man2/rename.2.html), [fsync(2)](https://www.man7.org/linux/man-pages/man2/fsync.2.html). These references inform this protocol; they are not substitute cross-platform qualification evidence.
